# 画面録画の音声同期問題を完全に解決した話

**— 12秒のずれを0.2秒以内に追い込むまでの全記録 —**

---

## はじめに

Python で画面録画アプリを作った。画面キャプチャ、システム音声、マイク音声を同時に録画して MP4 に結合する、よくあるやつだ。

で、再生してみたら **音声が12秒早い**。

「まあフレームレート制御入れれば直るでしょ」と思った自分が甘かった。ここから始まる2日間の地獄のデバッグと、最終的に全てを解決した3つのブレイクスルーを共有する。

## 問題の全体像

3つのストリームを同時に録画して1つの MP4 に結合する:

```
画面 (dxcam/mss) ──→ rawvideo パイプ ──→ ffmpeg ──→ video.mp4
システム音声 (WASAPI) ──→ WAV ファイル ─┐
マイク (PyAudioWPatch) ──→ WAV ファイル ─┴→ ffmpeg amix ──→ audio.wav
                                                              ↓
                                          ffmpeg merge ──→ output.mp4
```

シンプルに見えるが、**3つのストリームの時間軸を揃える** のが地獄だった。

---

## ブレイクスルー #1: パイプ書き込みの非ブロッキング化

### 問題

2800×1600 の rawvideo フレームは **1枚あたり13MB**。これを ffmpeg のパイプに書き込むと、libx264 のエンコードが追いつかずパイプバッファが満杯になり、`stdin.write()` がブロックする。

ブロック中は新しいフレームを取得できない。ブロック解除後に取得するフレームは **実際の画面より数秒遅れた内容** になる。

ログの数値は完璧（映像と音声の長さが一致）なのに、再生すると音声が3秒早い。**長さの問題ではなく、映像の内容が遅れている** という、ログだけでは見えない問題だった。

### 解決

```python
# パイプ書き込み専用スレッド
self._pipe_queue = queue.Queue(maxsize=30)

def write_frame(self, frame):
    # キューに入れるだけで即座に返る（ブロックしない）
    try:
        self._pipe_queue.put_nowait(data)
    except queue.Full:
        # キュー満杯 = エンコーダが追いつかない → 古いフレームを捨てて最新を入れる
        self._pipe_queue.get_nowait()
        self._pipe_queue.put_nowait(data)

def _pipe_writer_worker(self):
    # 別スレッドで実際のパイプ書き込みを行う
    while True:
        data = self._pipe_queue.get()
        if data is None:
            break
        self._video_process.stdin.write(data)
```

**キモ**: `write_frame()` を呼ぶキャプチャワーカーは絶対にブロックされない。パイプが詰まっても、キャプチャワーカーは常に最新のフレームを取得し続ける。

## ブレイクスルー #2: WASAPI ループバックの無音問題

### 問題

46秒の録画で、マイク WAV は46秒なのにシステム音声 WAV が43秒しかない。**3秒分のデータが消えている。**

原因は WASAPI ループバックの仕様:

> **オーディオエンジンがデバイスにデータを送信している間のみ、キャプチャデータが利用可能になる。**
> — Microsoft 公式ドキュメント

つまり、**システムが音を出していない間はデータが来ない。** コールバックモードでもブロッキング read モードでも同じ。これは仕様であり、バグではない。

### 試して失敗した方法

1. **コールバック内で無音挿入** → コールバック自体が来ないので発動しない
2. **ブロッキング read モード** → `read()` が無音時にブロックして返らない
3. **末尾に無音を追加** → 途中の無音区間が消えるので、末尾を足しても内容がずれる

### 解決: ポーリング + タイマーベース無音挿入

```python
def _sys_audio_read_worker(self):
    interval = CHUNK_SIZE / sample_rate  # 約 0.085秒
    silence = b'\x00' * (CHUNK_SIZE * channels * SAMPLE_WIDTH)
    next_write_time = time.perf_counter()

    while not self._stop_event.is_set():
        now = time.perf_counter()
        if now < next_write_time:
            time.sleep(0.005)
            continue

        available = stream.get_read_available()
        if available >= CHUNK_SIZE:
            data = stream.read(CHUNK_SIZE)
            wav.writeframes(data)
        else:
            # データなし = 無音区間 → 自分で無音を書き込む
            wav.writeframes(silence)

        next_write_time += interval
```

**キモ**: WASAPI がデータを返さなくても、**タイマーで一定間隔で無音を自分で書き込む**。これで WAV の長さが実時間と正確に一致する。

結果:
```
変更前: システム音声-マイクの差 = -2〜-6秒
変更後: システム音声-マイクの差 = +0.169秒 ✅
```

## ブレイクスルー #3: 開始時刻の統一

### 問題

3つのストリームの開始時刻がバラバラ:

```
映像開始:       0.000秒
システム音声開始: +0.182秒
マイク開始:     +0.237秒
```

0.2秒の差は小さく見えるが、結合時にこれを無視すると映像と音声の先頭がずれる。

### 解決

一番遅いストリーム（マイク）を基準にして、映像の先頭をトリム:

```python
latest_start = max(video_start, sys_start, mic_start)
video_trim = latest_start - video_start

# 結合時
ffmpeg -ss {video_trim} -i video.mp4 -i audio.wav -shortest output.mp4
```

## おまけ: 踏んだ地雷たち

### h264_mf は使うな

Windows Media Foundation の H.264 エンコーダ（`h264_mf`）は動作テストに成功するが、**内部バッファリング遅延が数秒ある**。入力フレームを受け取ってから出力するまでに3秒かかるため、映像の内容が3秒遅れる。ログの数値は完璧なのに再生すると音声が早い、という最も厄介なパターン。

### GT 1030 は NVENC 非搭載

NVIDIA GPU があるのに `h264_nvenc` が失敗する。GT 1030 は Pascal 世代のローエンドで、コスト削減のため NVENC ブロックが省かれている。GTX 1050 以上が必要。

### DPI スケーリングは座標系を壊す

Windows の 150% スケーリング環境で、tkinter の座標（論理ピクセル）と mss のキャプチャ座標（物理ピクセル）がずれる。`SetProcessDpiAwareness(2)` を `main()` の最初に呼ぶだけで解決。

### PyAudioWPatch の stop_stream() は80秒ハングする

マイクストリームの `stop_stream()` が無限にブロックすることがある。別スレッドで実行して5秒でタイムアウトする対策が必要。

## 教訓

1. **ログの数値が完璧でも同期がずれることがある。** 長さの問題ではなく、内容のタイミングの問題。パイプのブロックは長さに影響しないが、内容を遅らせる。

2. **WASAPI ループバックは無音時にデータを返さない。** これは仕様。コールバックでもブロッキング read でも同じ。自分でタイマーを回して無音を挿入するしかない。

3. **リアルタイムエンコードは高解像度で破綻する。** 3840×2160 の rawvideo（24MB/フレーム）を 15fps でパイプに書き込むのは、CPU エンコーダには荷が重い。パイプ書き込みの非ブロッキング化が必須。

4. **HW エンコーダは万能ではない。** GT 1030 は NVENC なし、h264_mf はバッファリング遅延あり。libx264 veryfast が最も信頼できるフォールバック。

5. **問題を分離して考える。** 「音声が早い」は1つの問題に見えるが、実際は「パイプブロック」「WASAPI 無音」「開始時刻差」の3つの独立した問題の合成だった。
