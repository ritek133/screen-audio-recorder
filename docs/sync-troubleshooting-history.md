# 画面・音声同期問題のトラブルシューティング履歴

## 環境情報

- OS: Windows 10/11
- GPU: NVIDIA GeForce GT 1030（NVENC 非対応）
- 画面解像度: 2600〜3840×1600〜2160（高DPI環境）
- オーディオ: Jabra Link 390（USB）、ループバック 48000Hz、マイク 44100Hz
- ffmpeg: 7.1-essentials_build (gyan.dev)
- エンコーダ: libx264 veryfast（HW エンコーダ利用不可）

---

## 問題1: 画面が音声より遅れる（最初は12秒）

### 原因の変遷

| 試行 | 原因分析 | 対策 | 結果 |
|------|---------|------|------|
| 1 | フレームレート制御なし。キューからフレームを連続書き込み | FPSタイマーで書き込み間隔を制御 | 12秒→5秒に改善 |
| 2 | write_frame のバイト数不一致でフレーム境界ずれ | cv2.resize + バイト数検証 | 部分的改善 |
| 3 | ffprobe が存在せず長さ計測が常に「不明」 | wave モジュール + ffmpeg -i で長さ取得 | 計測可能に |
| 4 | 音声マージ時にサンプルレート不統一（48000Hz + 44100Hz） | `-ar 44100` でサンプルレート統一 | マージ品質改善 |

### 根本原因

rawvideo パイプ + `-r 15` の方式では、ffmpeg は受け取ったフレーム数 ÷ FPS で映像の長さを決める。フレーム数が実時間と一致しなければ必ずずれる。

## 問題2: 音声が画面より早い（3〜6秒）

### 原因の変遷

| 試行 | 原因分析 | 対策 | 結果 |
|------|---------|------|------|
| 1 | `-ss` トリムが過剰（二重補正） | `-itsoffset` に変更 | 方向は改善 |
| 2 | h264_mf のバッファリング遅延（数秒） | h264_mf を候補から除外 | 3秒に改善 |
| 3 | write_frame のパイプ書き込みがブロック | パイプ書き込み専用スレッド + キュー | パイプドロップ0に |
| 4 | パイプキュー満杯で最初のフレームが繰り返される | キューサイズ 5→30 に拡大 | 部分的改善 |
| 5 | ffmpeg 初期化中に同じフレームがキューに溜まる | _first_pipe_write_done で実際の書き込み完了を待つ | 改善 |
| 6 | 固定3秒オフセット | 開始時刻差 + パイプドロップ計測で動的計算 | 改善 |

### 根本原因

高解像度（2800×1600）の rawvideo を ffmpeg パイプに書き込む際、libx264 のエンコードが追いつかずパイプがブロック。ブロック中に新しいフレームが取得できず、映像の内容が実時間より遅れる。

## 問題3: システム音声 WAV が実時間より短い（2〜6秒不足）

### 原因の変遷

| 試行 | 原因分析 | 対策 | 結果 |
|------|---------|------|------|
| 1 | WASAPI ループバックが無音時にコールバックを呼ばない | コールバック内で間隔計測 + 無音挿入 | 効果なし |
| 2 | コールバックは来ているがデータが短い可能性 | ブロッキング read モードに変更 | 効果なし |
| 3 | stream.read() も無音時にブロックして返らない | ★未実装: ポーリング + タイマーベース無音挿入 | — |

### 根本原因

**WASAPI ループバックは仕様として無音時にデータを返さない。** Microsoft 公式ドキュメント:
> "オーディオエンジンがデバイスにデータを送信している間のみ、キャプチャデータが利用可能になる。"

コールバックモードでもブロッキング read モードでも、無音時はデータが来ない。

### 次のステップ（未実装）

**タイマーベースのポーリング方式:**
```python
while not stop:
    available = stream.get_read_available()
    if available >= CHUNK_SIZE:
        data = stream.read(CHUNK_SIZE)
        wav.writeframes(data)
    else:
        wav.writeframes(silence_chunk)  # 無音を自分で書き込む
    time.sleep(expected_interval)
```

## 問題4: 録画サイズが選択範囲と異なる

### 原因

Windows のディスプレイスケーリング（DPI スケーリング）により、tkinter の論理ピクセル座標と mss の物理ピクセル座標がずれていた。

### 対策

`main()` の先頭で `SetProcessDpiAwareness(2)` を呼び出し、Per-Monitor DPI Aware に設定。

### 結果

✅ 解決

---

## 問題5: 画面が止まる（先頭2秒間同じフレーム）

### 原因

ffmpeg の libx264 初期化中にパイプキューに同じフレームが溜まり、初期化完了後に一気に書き込まれる。

### 対策

1. パイプキューサイズを 5→30 に拡大
2. `_first_pipe_write_done` イベントで ffmpeg が実際にデータを消費し始めてから音声録音を開始

### 結果

部分的改善（高解像度環境では依然として発生する可能性あり）

---

## 問題6: マイクストリームのクローズが80秒ハング

### 原因

PyAudioWPatch の `stop_stream()` が無限にブロックする。

### 対策

`stop_stream()` を別スレッドで実行し、5秒でタイムアウト。

### 結果

✅ 解決

## 問題7: recording_start_time がリセットされない

### 原因

2回目の録画で前回の `recording_start_time` が残り、壁時計時間が異常に大きくなる。

### 対策

`start()` で `recording_start_time = None` と `recording_wall_time = 0.0` をリセット。

### 結果

✅ 解決

## 最終結果（2026-05-06）

### 解決済み

| 問題 | 解決策 | 最終状態 |
|------|--------|---------|
| 画面が音声より12秒遅れる | FPSタイマー + パイプ書き込み専用スレッド | ✅ 映像-音声差 0.25秒 |
| システム音声が2〜6秒短い | ポーリング + タイマーベース無音挿入 | ✅ システム音声-マイク差 0.17秒 |
| 録画サイズが選択範囲と異なる | SetProcessDpiAwareness(2) | ✅ |
| マイクストリームが80秒ハング | stop_stream() に5秒タイムアウト | ✅ |
| recording_start_time リセット漏れ | start() でリセット | ✅ |

### 最終構成

```
画面キャプチャ: dxcam (DXGI Desktop Duplication API) 優先
               → mss (GDI) フォールバック

映像エンコード: libx264 veryfast crf 18
               ffmpeg 側で scale=1920:-2（高解像度時）
               パイプ書き込み専用スレッド（maxsize=30 キュー）

システム音声:   WASAPI ループバック
               ポーリング + タイマーベース無音挿入方式
               get_read_available() でデータ有無を確認
               データなし → 無音チャンクを自分で書き込む
               → WAV の長さが実時間と正確に一致

マイク:        PyAudioWPatch コールバックモード

音声マージ:    ffmpeg amix -ar 44100 -ac 2

結合:          ffmpeg -ss {video_trim} -i video.mp4 -i audio.wav
               -c:v libx264 -crf 18 -c:a aac -b:a 128k -shortest

DPI:           SetProcessDpiAwareness(2) Per-Monitor DPI Aware
```

### 学んだ教訓

1. **WASAPI ループバックは無音時にデータを返さない** — これは仕様。コールバックモードでもブロッキング read でも同じ。ポーリング + 自前の無音挿入が唯一の解決策。

2. **rawvideo パイプ + リアルタイムエンコードは高解像度で破綻する** — 3840×2160 の rawvideo（24MB/フレーム）をパイプに書き込むと、エンコーダが追いつかずブロックする。パイプ書き込み専用スレッドで非ブロッキング化が必要。

3. **ffmpeg の `-r` は入力フレームレートの宣言** — 実際に送ったフレーム数 ÷ fps が映像の長さになる。フレーム数を正確に制御しないと同期がずれる。

4. **h264_mf (Media Foundation) はリアルタイム録画に不向き** — 内部バッファリング遅延が数秒あり、映像の内容が遅れる。

5. **DPI スケーリングは座標系を壊す** — tkinter（論理ピクセル）と mss（物理ピクセル）の座標が一致しない。SetProcessDpiAwareness で統一が必要。

6. **GT 1030 は NVENC 非搭載** — ローエンド GPU はハードウェアエンコーダを持たない。CPU エンコード（libx264 ultrafast/veryfast）がフォールバック。

## 問題8: dxcam が選択領域を無視してフル画面キャプチャ（2026-05-07）

### 原因

`_capture_worker_dxcam` で `camera.grab()` を region パラメータなしで呼んでいたため、`self._region` に選択領域が保存されていても無視され、常にフル画面がキャプチャされていた。

### 対策

`camera.grab(region=(left, top, right, bottom))` で指定領域のみをキャプチャするように修正。

### 結果

✅ 解決

---

## 問題9: ffmpeg 結合タイムアウト（5分録画で120秒超過）（2026-05-07）

### 原因

映像+音声結合時に `-c:v libx264` で再エンコードしていたため、5分の録画でも120秒以上かかりタイムアウト。2〜3時間の録画では実用不可能。

### 対策

映像は録画時に既に H.264 エンコード済みのため、結合時は `-c:v copy`（ストリームコピー）に変更。再エンコード不要で数秒〜数十秒で完了。

### 結果

✅ 解決

---

## 問題10: 音声マージの PermissionError（Windows ファイルロック）（2026-05-07）

### 原因

`_merge_wav_files` で元の `.audio.wav` を `unlink` した後、`.merged.wav` を `.audio.wav` にリネームしようとした際に Windows のファイルハンドル解放遅延で `PermissionError` が発生。元ファイルは削除済みなのにリネームも失敗し、音声ファイルが消失。

### 対策

1. `shutil.move` + リトライ（最大5回、0.5秒間隔）で堅牢化
2. 最終的に失敗した場合は `.merged.wav` をそのまま使用
3. VideoEncoder 側でも `.audio.wav` が見つからない場合に `.audio.wav.merged.wav` をフォールバック探索

### 結果

✅ 解決

## 問題11: 文字起こしの output_path 上書き（連続録画時）（2026-05-07）

### 原因

`_on_transcribe_complete` で `self._current_output_path` を参照していたが、次の録画開始で上書きされるため、前の録画の文字起こし結果が新しい録画のパスでメモに保存されてしまう。

### 対策

`stop_recording()` で `transcribe_async` を呼ぶ際に `output_path` をクロージャでキャプチャし、コールバックに渡すように変更。

### 結果

✅ 解決

## 問題12: 起動時にコンソールウィンドウが表示される（2026-05-07）

### 原因

PyInstaller spec ファイルで `console=True` が設定されていた。

### 対策

1. `screen_audio_recorder.spec`: `console=False` に変更
2. `main.py`: `ShowWindow(hwnd, 0)` で保険的にコンソールを非表示
3. すべての `subprocess.run` / `subprocess.Popen` に `creationflags=CREATE_NO_WINDOW` を追加

### 結果

✅ 解決

## 問題13: 起動時に録画ボタンが即座に使えない（モデルロード待ち）（2026-05-07）

### 原因

Whisper モデルのロードが同期的に行われ、メインウィンドウ表示前にブロックされていた。

### 対策

1. `Transcriber` に `lazy_load=True` パラメータを追加
2. メインウィンドウ表示後にバックグラウンドスレッドでモデルをロード（`load_model_async()`）
3. ロード中はステータスバーに「モデル読み込み中...」と表示し、録画ボタンを無効化
4. ロード完了後に `set_ready()` で録画ボタンを有効化

### 結果

✅ 解決
