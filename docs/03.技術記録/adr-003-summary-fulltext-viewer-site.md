# ADR-003: 録音メモの要約・全文閲覧サイトの UI 方式

## ステータス

決定済み（Accepted）

## 日付

2026-09-21

## コンテキスト

アプリが出力する録音メモ（`memos.json`）を、ブラウザで**要約の一覧**と**全文**を
閲覧できるサイト機能を追加したい。UI 方式を決めるにあたり、複数のサンプルを作成し、
実際に触って比較したうえで採用案を選定した。

### 想定するデータ規模

選定の初期段階では「少数・短文」を想定していたが、確認の結果、実運用では以下の規模を前提とすべきと判明した。

| 項目 | 規模 |
|------|------|
| メモ数 | 数百件 |
| 要約（`summary`） | 約 1,000 文字 |
| 全文（`body`） | 10,000 文字超 |

この規模は UI 方式の判断に直結する（一覧に全文や長い要約を出せない、全件描画は重い、など）。

### ソースデータ（`memos.json`）

| サイト表示 | フィールド | 備考 |
|-----------|-----------|------|
| タイトル   | `theme` | 空なら「無題」 |
| 要約       | `summary` | 一覧では省略表示 |
| 全文       | `body` | 詳細でのみ表示 |
| 日時       | `created_at` | |
| （非表示） | `output_file` | ローカルフルパスを含むため**サイトには出力しない** |

- `body` または `summary` が空のメモは一覧から除外する。

## 検討案

比較用のサンプルを `docs/site-samples/` に作成した。

### 案A: サマリーカード + モーダル全文（`sample-a-cards-modal.html`）

要約カードを一覧表示し、クリックでモーダルに全文を表示。単一 HTML・依存ゼロ。

- メリット: 最小構成、すぐ公開できる、少数なら見栄えが良い
- デメリット: 全文 1 万字超をモーダルで読むのは窮屈。記事ごとの URL がなく共有・SEO に弱い

### 案B: 一覧/詳細 2ペイン（`sample-b-two-pane.html`）【採用】

左に一覧＋要約（省略表示）、右に要約＋全文を表示。全文は既定で折り畳み。単一 HTML・依存ゼロ。

- メリット: 一覧と本文を同時に見られ、要約を次々見比べやすい。全文の折り畳みで長文でも画面が埋まらない
- デメリット: 記事ごとの URL がない。全件を単一 JSON でロードするため、大規模化すると初期ロードが重い

### 案C: 静的サイトジェネレータ（Astro）（`sample-c-astro-ssg.md`）

`memos.json` から各メモの独立ページをビルド。要約=一覧、全文=個別ページ。

- メリット: 全文を個別ページに分割でき、初期ロードは要約のみで済むため規模に強い。URL・SEO・RSS に有利
- デメリット: Node.js とビルド工程が必要（本リポジトリは現状 Python 主体）。学習・保守コストが高い

## 決定

**案B（一覧/詳細 2ペイン）を採用する。** あわせて次を採用時の仕様とする。

- 一覧（左ペイン）: タイトルと要約を省略表示（要約は 2 行にクリップ）
- 詳細（右ペイン）: 要約は常時表示、**全文は既定で折り畳み（`<details>`、クリックで展開）**
- 検索: タイトル・要約に対するクライアントサイド絞り込み
- 一覧の描画: 段階描画（初期 50 件 + 「もっと見る」）で数百件でも軽く保つ
- `output_file` は表示しない（プライバシー保護）

### 選定理由

- 数百件の要約を「見比べる」用途に、一覧と本文を同画面に置ける 2ペインが最も合う。
- 全文 1 万字超はモーダル（案A）だと読みづらく、折り畳みで既定は隠せる案B が扱いやすい。
- 案C（SSG）は規模面で最有力だが、現状 Python 主体のリポジトリに Node.js のビルド基盤を
  持ち込むコストが見合わないと判断。まずは依存ゼロの案B で導入し、規模の拡大が顕著になった
  段階で案C（または後述の遅延ロード方式）への移行を再検討する。

## 制約事項・大規模化への留意

- 全文 1 万字 × 数百件を 1 つの `memos.json` にすると、10MB 規模の初期ロードになる。
  案B の「全件を単一 JSON でロード」方式は、件数増加に伴い初期表示が重くなる。
- 将来的な対策として、**要約のみの軽量インデックス + 全文は選択時に個別取得（遅延ロード）** への
  分割を想定しておく。これにより案B の 2ペイン UI を保ったまま大規模化に耐えられる。
- クライアントサイド検索も全件を対象にするため、件数が非常に多くなればサーバー側検索や
  インデックス化の検討が必要になる。

## 影響範囲

### サンプル（本 ADR の選定成果物）

- `docs/site-samples/sample-b-two-pane.html`（採用案のモック。全文折り畳み対応）
- `docs/site-samples/sample-a-cards-modal.html` / `sample-c-astro-ssg.md`（比較用・不採用）
- `docs/site-samples/generate_sample_memos.py`（大規模サンプルデータ生成スクリプト）
- `docs/site-samples/memos.sample.json`（軽量サンプルデータ・コミット対象）
- `docs/site-samples/README.md`（プレビュー手順・設計論点）

### 今後の実装（別タスク）

- `memos.json` を読み込む本番用サイトの実装（採用案B をベースに）
- 大規模化に備えた「要約インデックス + 全文遅延ロード」方式の検討
- 公開方法（静的ホスティング）と、必要なら `.github/workflows/` への build & deploy 追加

## 備考

- サンプルのデータソースには実データ `memos.json` ではなく、無害な生成データを用いた。
  実データはローカルのみに置き、`.gitignore` によりコミット対象外としている。
- 実データの文字起こしには不適切な表現が含まれ得るため、本 ADR には本文を転記していない。
