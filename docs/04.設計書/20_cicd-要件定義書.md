# CI/CD パイプライン要件定義書

## 1. 概要

Screen Audio Recorder プロジェクトのリリース運用を自動化する。  
手動で行っていたビルド→リリースアップロードを GitHub Actions で自動化し、  
PR ベースの開発フローを確立する。

## 2. 運用フロー全体像

```
開発者が機能ブランチで作業
    ↓
PR 作成（main ブランチ向け）
    ↓
CI: 自動テスト実行（pytest）
    ↓
CI: セキュリティチェック（機密情報・個人情報の検出）
    ↓
レビュー & 承認
    ↓
main ブランチへマージ
    ↓
バージョンタグ push（vX.Y.Z）
    ↓
CD: GitHub Actions でビルド（PyInstaller）
    ↓
ビルド成果物の後処理（リネーム・zip作成）
    ↓
GitHub Releases に自動アップロード
```

## 3. 要件一覧

### 3.1 PR 時の自動テスト（CI）

| 項番 | 要件 | 詳細 |
|------|------|------|
| CI-1 | トリガー条件 | main ブランチへの PR 作成・更新時に自動実行 |
| CI-2 | テスト実行 | pytest を実行し、全テストがパスすることを確認 |
| CI-3 | Python バージョン | Python 3.10 以上（pyproject.toml の requires-python と一致） |
| CI-4 | 依存インストール | `pip install -e ".[dev]"` で開発依存を含めてインストール |
| CI-5 | 結果表示 | テスト結果を PR のステータスチェックとして表示 |
| CI-6 | ブランチ保護 | CI パスを main へのマージ条件とする（GitHub 設定） |

### 3.2 ビルド & リリース（CD）

| 項番 | 要件 | 詳細 |
|------|------|------|
| CD-1 | トリガー条件 | バージョンタグ（`v*`）の push で自動実行 |
| CD-2 | ビルド環境 | Windows runner（`windows-latest`）を使用 |
| CD-3 | ビルドツール | PyInstaller で `screen_audio_recorder.spec` を使用してビルド |
| CD-4 | ビルド成果物 | `dist/screen-audio-recorder/` ディレクトリ一式 |
| CD-5 | テスト前提 | ビルド前に pytest を実行し、パスした場合のみビルドに進む |

### 3.3 ビルド後処理

| 項番 | 要件 | 詳細 |
|------|------|------|
| POST-1 | exe リネーム | `screen-audio-recorder.exe` → `screen-audio-recorder-vX.Y.Z.exe` |
| POST-2 | zip 作成 | `dist/screen-audio-recorder/` の内容を `screen-audio-recorder-vX.Y.Z-full.zip` に圧縮 |
| POST-3 | zip 構造 | zip のルート直下に `screen-audio-recorder.exe` と `_internal/` が並ぶ構造 |
| POST-4 | バージョン取得 | タグ名（`v0.2.0` → `0.2.0`）からバージョン番号を抽出 |

### 3.4 リリースアップロード

| 項番 | 要件 | 詳細 |
|------|------|------|
| REL-1 | リリース作成 | タグに対応する GitHub Release を自動作成 |
| REL-2 | アセット添付 | exe ファイルと zip ファイルの両方をリリースアセットとして添付 |
| REL-3 | リリースノート | 自動生成（前回タグからの変更コミット一覧）またはドラフトとして作成 |
| REL-4 | プレリリース除外 | プレリリースにはしない（自動更新の対象外になるため） |
| REL-5 | タグ形式 | `v` プレフィックス必須（例: `v0.2.0`） |

### 3.5 セキュリティチェック（CI）

| 項番 | 要件 | 詳細 |
|------|------|------|
| SEC-1 | シークレット検出 | API キー、トークン、パスワード等のハードコードされた認証情報を検出する |
| SEC-2 | 個人情報検出 | メールアドレス、電話番号、住所等の個人を特定できる情報（PII）を検出する |
| SEC-3 | 機密ファイル検出 | `.env`、秘密鍵ファイル（`.pem`, `.key`）、認証情報ファイルがコミットに含まれていないことを確認 |
| SEC-4 | AWS 認証情報検出 | AWS Access Key ID / Secret Access Key のパターンを検出する |
| SEC-5 | ローカルパス検出 | ローカル環境のフルパス（`C:\Users\...`、`/home/...`）がソースコードに含まれていないことを確認 |
| SEC-6 | 実行タイミング | PR 時の CI で毎回実行し、検出された場合はマージをブロック |
| SEC-7 | 検出対象 | PR の差分（変更ファイル）のみをスキャン。既存コード全体のフルスキャンは行わない |

### 3.6 ブランチ保護

| 項番 | 要件 | 詳細 |
|------|------|------|
| BR-1 | main への直接 push 禁止 | PR 経由でのみ main を変更可能にする |
| BR-2 | 承認必須 | 最低1名のレビュー承認を必須とする |
| BR-3 | CI パス必須 | テスト CI およびセキュリティチェックがパスしていないとマージ不可 |
| BR-4 | ステータスチェック | CI ワークフローのジョブ名（test, security）をステータスチェックとして登録 |

## 4. 前提条件・制約

| 項目 | 内容 |
|------|------|
| リポジトリ | GitHub（パブリックまたはプライベート） |
| ビルド OS | Windows（PyInstaller でネイティブ exe を生成するため） |
| Python | 3.10 以上 |
| ビルドツール | PyInstaller（既存の .spec ファイルを使用） |
| 成果物の命名規則 | README.md 記載のアセット命名規則に準拠 |
| 自動更新との互換性 | `updater.py` のリリース検知ロジックと整合すること |

## 5. 自動更新との整合性

アプリ内蔵の自動更新機能（`updater.py`）は以下のルールでリリースを検知する:

- GitHub Releases API からリリース一覧を取得
- プレリリースは対象外
- アセット名のパターンでフル更新/通常更新を判定:
  - `*-full.zip` → フル更新
  - `*.exe` → 通常更新
  - 両方存在する場合は zip（フル更新）を優先

CI/CD パイプラインの成果物は、この判定ロジックと完全に一致する命名にする必要がある。

## 6. リリースフロー（自動化後）

### 開発者の操作

1. `src/screen_audio_recorder/__init__.py` の `__version__` を更新
2. `pyproject.toml` の `version` を同じ値に更新
3. コミット & PR 作成
4. レビュー承認を得てマージ
5. タグ作成 & push: `git tag v0.2.0 && git push origin v0.2.0`

### 自動実行される処理

6. GitHub Actions がタグ push を検知
7. pytest でテスト実行
8. PyInstaller でビルド
9. 成果物のリネーム & zip 作成
10. GitHub Release を作成し、アセットをアップロード

## 7. 非機能要件

| 項目 | 要件 |
|------|------|
| ビルド時間 | 15分以内（GitHub Actions の無料枠を考慮） |
| 再現性 | 同じタグからは同じ成果物が生成されること |
| シークレット管理 | GITHUB_TOKEN のみ使用（追加のシークレット不要） |
| 失敗時の通知 | GitHub のデフォルト通知（メール）で十分 |
