# 開発ガイド

## 1. 基本ルール

- **コードを変更する前に、必ずブランチを作成する**
- main ブランチへの直接 push は禁止（ブランチ保護で強制）
- すべての変更は PR 経由でマージする

---

## 2. ブランチ運用

### 2.1 ブランチ構成

```
main（常にリリース可能な状態）
  │
  ├── feature/xxx   ← 新機能
  ├── fix/xxx       ← バグ修正
  ├── refactor/xxx  ← リファクタリング
  ├── docs/xxx      ← ドキュメントのみ
  └── chore/xxx     ← CI・依存更新等の雑務
```

### 2.2 ブランチ命名規則

| プレフィックス | 用途 | 例 |
|---------------|------|-----|
| `feature/` | 新機能追加 | `feature/bedrock-transcribe` |
| `fix/` | バグ修正 | `fix/video-encoder-crash` |
| `refactor/` | リファクタリング | `refactor/memo-store-async` |
| `docs/` | ドキュメントのみの変更 | `docs/update-user-manual` |
| `chore/` | CI、依存更新、設定変更 | `chore/update-dependencies` |

### 2.3 命名のポイント

- 英語の短い説明をハイフン区切りで書く
- 長すぎない（2〜4単語が目安）
- 何をやるブランチか名前だけで分かるようにする

---

## 3. 作業フロー

### 3.1 通常の開発作業

```bash
# 1. main を最新にする
git checkout main
git pull origin main

# 2. ブランチを作成（ここから作業開始）
git checkout -b feature/add-hotkey-support

# 3. コードを変更・コミット（こまめに）
git add src/screen_audio_recorder/gui/main_window.py
git commit -m "feat: ホットキー設定UIを追加"

git add src/screen_audio_recorder/recorder_controller.py
git commit -m "feat: グローバルホットキーで録画開始/停止"

# 4. リモートに push
git push -u origin feature/add-hotkey-support

# 5. GitHub で PR を作成（main ブランチ向け）
#    → CI が自動実行される（テスト + セキュリティチェック）

# 6. レビュー承認を得る → マージ（Squash merge）

# 7. ローカルを整理
git checkout main
git pull origin main
git branch -d feature/add-hotkey-support
```

### 3.2 ブランチの掃除

マージ済みブランチは溜めずに削除する。常にローカルにあるのは `main` + 作業中の1〜2本だけ。

```bash
# マージ済みローカルブランチを削除
git branch -d feature/add-hotkey-support

# リモートで削除されたブランチの追跡参照を掃除
git fetch --prune

# マージ済みブランチを一括確認（main 以外で残っているもの）
git branch --merged main
```

**GitHub 側の設定（推奨）**:
- Settings → General → Pull Requests → 「Automatically delete head branches」を有効化
- マージ時にリモートブランチが自動削除される

### 3.3 うっかり main で作業してしまった場合

```bash
# まだコミットしていなければ → そのまま新ブランチに移行できる
git checkout -b feature/xxx
# 変更内容がそのまま新ブランチに持ってこられる

# 既にコミットしてしまった場合
git branch feature/xxx          # 現在の位置でブランチを作成
git checkout main
git reset --hard origin/main    # main を元に戻す
git checkout feature/xxx        # 作業ブランチに移動
```

## 4. コミットメッセージ

### 4.1 形式

```
<タイプ>: <変更内容の要約>
```

### 4.2 タイプ一覧

| タイプ | 用途 | 例 |
|--------|------|-----|
| `feat` | 新機能 | `feat: Bedrock Transcribe バックエンドを追加` |
| `fix` | バグ修正 | `fix: 録画停止時にffmpegプロセスが残る問題を修正` |
| `refactor` | リファクタリング | `refactor: RecorderController を async 化` |
| `docs` | ドキュメント | `docs: 操作説明書にホットキー設定を追記` |
| `chore` | 雑務 | `chore: PyInstaller を 6.0 に更新` |
| `test` | テスト追加・修正 | `test: TranscriberのBedrock連携テストを追加` |

### 4.3 ルール

- 日本語で書いてOK
- 1行目は50文字以内を目安
- 「何をしたか」を動詞で始める
- 詳しい説明が必要なら空行を挟んで2行目以降に記述

---

## 5. PR（Pull Request）

### 5.1 PR の作り方

1. GitHub リポジトリページで「Compare & pull request」ボタンをクリック
2. または `gh pr create` コマンドで作成

### 5.2 PR タイトル

コミットメッセージと同じ形式:
```
feat: ホットキーによる録画開始/停止を実装
```

### 5.3 PR 説明文テンプレート

```markdown
## 概要
<!-- 何をやったか1〜2行で -->

## 変更内容
<!-- 具体的な変更のリスト -->
- 
- 

## テスト
<!-- どうやって動作確認したか -->
- [ ] pytest パス
- [ ] 手動動作確認

## 備考
<!-- レビュアーに伝えたいこと（あれば） -->
```

### 5.4 マージ戦略

**Squash merge** を使用する:
- 機能ブランチの複数コミットが1つにまとめられ、main の履歴がきれいに保たれる
- PR タイトルがマージコミットのメッセージになる

---

## 6. CI（自動チェック）

PR を出すと以下が自動実行される:

| チェック | 内容 | 失敗時 |
|---------|------|--------|
| test | pytest 全テスト実行 | マージ不可 |
| security | シークレット・個人情報の検出 | マージ不可 |

### 6.1 CI が失敗した場合

1. GitHub Actions のログを確認
2. 問題を修正
3. 修正をコミット & push → CI が自動で再実行される

```bash
# 修正して push すれば CI は自動で再実行される
git add .
git commit -m "fix: テスト失敗を修正"
git push
```

## 7. リリース手順

マージ後、リリースしたいタイミングで以下を実行する。

### 7.1 バージョン更新（PR として実施）

```bash
git checkout main
git pull origin main
git checkout -b chore/bump-v0.3.0
```

以下の2ファイルのバージョンを更新:
- `src/screen_audio_recorder/__init__.py` の `__version__`
- `pyproject.toml` の `version`

```bash
git add src/screen_audio_recorder/__init__.py pyproject.toml
git commit -m "chore: バージョンを v0.3.0 に更新"
git push -u origin chore/bump-v0.3.0
# → PR 作成 → マージ
```

### 7.2 タグ push（リリーストリガー）

```bash
git checkout main
git pull origin main
git tag v0.3.0
git push origin v0.3.0
```

### 7.3 自動実行される処理

タグ push 後、GitHub Actions が自動で:
1. テスト実行
2. PyInstaller でビルド
3. 成果物のリネーム & zip 作成
4. GitHub Release を作成し、アセットをアップロード

---

## 8. やってはいけないこと

| NG | 理由 |
|----|------|
| main に直接 push | ブランチ保護で拒否される |
| `.env` をコミット | セキュリティチェックで検出・ブロック |
| API キーをソースに埋め込む | セキュリティチェックで検出・ブロック |
| `git push --force` を main に対して実行 | 履歴が壊れる。他メンバーに影響 |
| ブランチを切らずに作業開始 | PR が出せない → マージできない |
